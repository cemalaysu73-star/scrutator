# R9 progress log: organisation-scoped sources

Resumable log for round R9 (organisation sources behind `--org`). Newest entries at the bottom of each section.

## Decisions

- D1. Organisation sources run in their own **organisation phase**, after the passive collection and before attribution
  (`scrutator/org/run.py`), through `Engine.run_module` like every other lookup (scope gate, audit, evidence). They have
  `phase = "org"` and are never offered to the planner, so a network owner name found by RDAP can never become a query.
- D2. The seed stays a domain. Legal names come from evidence only: the RDAP registrant of the seed apex **only when the
  vCard says it is an organisation** (`org` property, or `kind: org`), the Wikidata organisation item whose official
  website is the seed, the LEI that item records, or `--legal-name` (recorded in the signed audit log before any
  lookup). A registrant `fn` without an organisation marker is never used: it may be a natural person.
- D3. Only exact matches: GLEIF by LEI or exact legal name (no fuzzy completion), Wikidata by official website (P856)
  and, only when no website match exists and a legal name is known, by exact English label. Several exact matches are
  shown as ambiguous, never merged.
- D4. ransomware.live rejected (keyless tier is personal use only; false-positive risk). Telegram, Medium rejected for
  handle checks (status does not tell), Substack rejected (terms forbid crawling), Reddit rejected (blocked, OAuth).
- D5. Every stored record from a source that also returns people (GitHub org/members, package registries) is a fixed
  projection without person fields; free text (descriptions) has e-mail addresses replaced before storage.
- D6. `--code-leaks` needs `--org`, an authorisation (`--self` or `--engagement FILE`, confirmed) and
  `SCRUTATOR_GITHUB_TOKEN`; it reads only the confirmed organisation's own public repositories, capped, and stores a
  salted fingerprint and a 2+2 character mask, never the value.
- D7. Attribution: a new signal `org_record` (a registry or Wikidata lists the domain as an official website of the
  organisation, or of its parent or subsidiary). Rule set 2; bundles made by rule set 1 are still re-derived when they
  hold no organisation evidence (the signal cannot fire on them).

## More decisions

- D8. The shipped sample audits (docs/examples/audit, en and tr) state the risk rule set of the tool that made them.
  Rule set 5 made them fail `content derivable`, as rule set 4 did in R8; they were regenerated the R8 way (same signed
  bundle, same engagement and branding, `audit --from-bundle`). The bundle bytes are unchanged; the PDFs were checked for
  local paths (none).
- D9. OpenCorporates and UK Companies House were NOT built: the keyed, documented-only modules were deprioritised for the
  keyless sources. Their rows in the probe table stay "keyed, not live-verified"; docs/organisation.md says they are not
  implemented yet.
- D10. Handles live in the organisation phase (`handles`), not in the `--brand` platform pack: the brand module only asks
  platforms the org's own site links to, and Bluesky's check is an API call with a query string the pack and replay do
  not model. Telegram, Medium, Substack, Reddit stay excluded (probe table).
- D11. Names first seen in the organisation phase are resolved once by DNS at its end (cap 50); before that fix a
  repo-named host stayed an unchecked claim.
- D13. Found in self-review after the first commit: the legal-name derivation reused the RDAP module's `registrant`
  edges, which come from vCard `fn` or `org`, so an individual registrant's name could have been queried. It now
  re-reads the cited RDAP answer and accepts a registrant only with an `org` property or `kind: org` (tested).
- D12. Commits: the round was implemented in one pass across shared files (cli, verify, egress, replay, tests); the
  intermediate states were never run green, so it is committed as one commit rather than eight untested ones.
