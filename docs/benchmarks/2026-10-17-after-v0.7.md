# Scrutator after v0.7, against the same tools and targets

All runs in this document were made on 2026-10-20 (the file keeps the name the round was planned under). Same
harness (`bench/run_bench.py`), same four frozen targets, same 900 s timeout, same competitors (sublist3r 1.0,
dnsrecon 0.10.1, knockpy 9.0.0) as `2026-10-17-baseline.md` and `2026-10-17-after-v0.6.md`. The criterion and the
targets of the frozen criterion (see [docs/benchmarks.md](../benchmarks.md)) were not touched.

Three kinds of run, all from this machine and network:

| Run | Code | What it is |
|---|---|---|
| **After** | `c86a463` (v0.7.0 plus the last speed-up) | `bench/run_bench.py --date 2026-10-20-v07`, all four tools, 18:50 to 18:56 |
| **Before** | `f1715b3` (v0.6.0) | the same harness with the competitors' results reused and only Scrutator re-run through a wrapper that runs the v0.6 source, `--date 2026-10-20-v06`, 18:56 to 19:02: **the same hour as the After run**, but not the same quota state (see "What distorts this comparison") |
| Timing | both | `bench/time_runs.py`: the benchmark's own Scrutator command on owasp.org, three runs of each version taking turns, five minutes apart |

Raw results: `bench/results/2026-10-20-v07/`, `bench/results/2026-10-20-v06/`. The per-target Scrutator extras
(tiers, findings by tier, the harness's own resolver verdict on each name) are in `tables.md` and
`scrutator.result.json` of each. An earlier After run at `5381787` (before the last speed-up, kept out of git as
scratch) is quoted where it differs.

## Verdict on the frozen criterion

Recall at least the best competitor on every truth target, every result evidence-backed, bundle verifies.

| Target | Truth | Scrutator v0.7 recall | Best competitor | Evidence-backed | Bundle verifies (pinned) | Tamper detected | Met |
|---|---|---|---|---|---|---|---|
| zonetransfer.me | 31 zone names (published AXFR dump) | 13% (4 of 31; 27% of the 15 host names) | knockpy 6% | 100% (6 of 6) | PASS | yes | yes, but 87% of the zone is reached by no tool |
| example.com | 1 live name | 100% | sublist3r and knockpy 100% | 100% (499 of 499) | PASS | yes | yes (tie) |
| nmap.org | 4 live names | 100% | knockpy 100% | 100% (349 of 349) | PASS | yes | yes (tie) |
| owasp.org | 53 live names | 89% (47) | knockpy 83% (44) | 100% (125 of 125) | PASS | yes | yes |

**On the numbers the criterion is met on all four targets, as it was for v0.6.** Read it with the limits of
`2026-10-17-after-v0.6.md`, which still hold: two truth sets are one and four names, three are circular (the union
of what the tools found), and the one real truth set shows 13%. v0.7 did not set out to move recall; it set out to
make the result honest about what is a host, and to make the scan fast. An
earlier run at `5381787` (taken before my other runs of the day had used the quotas) gave owasp.org 97% (60 live
names) against knockpy's 92%; the run above gives 89% against 83%. Scrutator's `hackertarget` module failed with
"daily quota used up" on owasp.org in the After run (the last target) and on all four targets in the Before run, and
CertSpotter answered 429 on three of four; knockpy found 122 names here against 134 earlier, which fits it losing
HackerTarget too, but its log does not say. Neither run measures the best these tools can do on a day with quota.

## Speed

Target set for this round: an owasp.org scan in 30 s or less when sources respond, with the same verified names and
unchanged evidence content addressing.

**Result: not met on the median. 86.1 s → 36.1 s (a factor of 2.4); one run in three was under 30 s.**

CLI wall time of the benchmark's own command on owasp.org (`scan --ai off --no-summary --bundle`), the two versions
taking turns, five minutes apart, 19:03 to 19:34:

| Run | v0.6 | v0.7 |
|---|---:|---:|
| 1 | 75.8 s | 36.9 s |
| 2 | 86.1 s | 36.1 s |
| 3 | 117.5 s | 21.7 s |
| **Median** | **86.1 s** | **36.1 s** |

All six runs reported the same 48 live names. In every run crt.sh answered 502, Common Crawl did not connect,
CertSpotter answered 429 and HackerTarget's quota was gone, for both versions (the failed-source lists are identical
in all six), so these are the runs of a bad day for the sources, not of a good one. A first set of 3 + 3 runs earlier the same day (at `5381787`, before the last
two speed-ups; 40.6, 42.4 and 40.9 s for v0.7 against 66.4, 100.9 and 146.4 s for v0.6) tells the same story; so
does the harness's own run: 15 to 53 s per target for v0.7 against 72 to 90 s for v0.6.

**Where the seconds go** (`bench/profile_scan.py`, one instrumented scan of owasp.org per row; collection only, so
add about 3 s of Python start-up and 1 s of report and bundle for the CLI):

| | v0.6 scheduling (profile at `3186b58`) | v0.7 (profile at `c86a463`) |
|---|---:|---:|
| Collection | 93.7 s | 21.8 s |
| Round structure | 3 barrier rounds: 17 s (Common Crawl's connect timeouts), 6.5 s, then 70 s (RDAP of 50 addresses at concurrency 4) | no rounds: a lookup starts when its entity is known |
| SQLite commits on the event loop | 21.8 s | 1.1 s |
| DNS queries on the wire | 807 (median 131 ms) | 452 (median 362 ms) |
| RDAP requests to rdap.org | 51 (one per address; retries not counted) | 20 (for 38 address lookups) |

What changed, in the order it paid off: a pipelined scheduler (no waiting for the slowest source of a round),
one transaction per lookup instead of one commit per record, a DNS pool and a parallel name-server warm-up, one
RDAP lookup per network (50 addresses of owasp.org are in 18 to 20 networks; the neighbours cite the record that
contains them), RIPEstat at its documented 8 concurrent, no sleeping through a long `Retry-After`, and A and CNAME
first for DNS so a name that does not exist costs two queries instead of six (the evidence is identical: a
negative answer for the other types is never recorded). Evidence content addressing is unchanged; the same 48 live
names came out in every run of both versions.

**What stops it from reaching 30 s** is not our code any more. In the 36 s runs and in the profile the last thing
running is RDAP for the final networks: `rdap.org` (behind Cloudflare) answers 429 with `Retry-After: 9` or `10`
once a client sends more than about ten requests in ten seconds (I measured it with a burst of 40 and with one
request every 0.5 s: the eleventh is refused), and an owasp.org scan needs about 20 of them. Pacing them (eight at
once, then one a second) or taking the 429 costs about the same, so the floor is near 20 s of RDAP. Next lever, not
done: network owners from RIPEstat's holder field instead of RDAP, or a `--fast` profile that leaves RDAP for
addresses out. Both change what the report holds, so they are choices for the user, not silent speed-ups; the
source policy (`--exclude-sources rdap`) already lets a user choose.

## What changed in v0.7

1. **Tiers.** Every name is `verified` (DNS resolves it, or a certificate or scan dated within 90 days names it),
   `claimed` (only a list names it), `stale` or `wildcard`, derived from evidence and re-derived by `verify`; the
   report, CLI and HTML lead with `N verified, M claimed` and fold the rest into counted groups.
2. **Speed**, as above.
3. **Source policy**: `--sources`, `--exclude-sources`, `--no-noncommercial`, recorded in the report, the manifest
   and the audit log, and checked by `verify`.
4. **Keyed sources** (VirusTotal, SecurityTrails, Shodan DNS) from environment keys only, and `scrutator sources`.
   They are implemented against the documented APIs and **not live-verified**: no keys, no accounts. The benchmark
   ran without keys, so none of them is in any number above.

## Where Scrutator still loses, ranked

1. **Time, still.** 36 s median against 3 to 6 s for knockpy. The floor is the rate limit of the service that gives
   network owners, plus 3 s of start-up; below that it means asking for less.
2. **Recall on the one real truth set**: 4 of 31 names in zonetransfer.me. 27 names (`vpn`, `owa`, the SRV and NAPTR
   owners) are reached by no passive tool; that is where a scope-gated zone transfer belongs (planned, active).
3. **Netcraft**: sublist3r's only working engine finds 6 live names on owasp.org that nobody else does. Its terms
   were never evaluated.
4. **Quota-limited sources decide the recall of a day.** HackerTarget's 50 calls a day and CertSpotter's rate limit
   are spent by a few scans from one address; part of this document's runs went without them. A cross-scan record of each source's quota would at least tell the user before the scan.
5. **The claimed tier is only as good as DNS at one moment.** A name that resolves tomorrow stays claimed in
   today's report; a name that resolves to a wildcard address and is vouched for by a certificate is verified
   although the harness cannot confirm it (the three nmap.org names at `5381787`).
6. **The keyed sources are untested against the real services.**
7. **Wildcard probe covers the apex only**, not wildcards below a delegated sub-zone (unchanged).
8. **Pseudo-truth is circular** and dnsrecon never produced a result (unchanged).

## Reproduce

```
python bench/run_bench.py --date 2026-10-20-v07                       # about 6 minutes
python bench/run_bench.py --date X --reuse-from bench/results/2026-10-20-v07 --rerun scrutator --scrutator <wrapper that runs the old source>
python bench/time_runs.py owasp.org --runs 3 --gap 300 --variant v0.6=<old src> --variant v0.7=<new src> --work DIR --keys bench/work/keys
python bench/profile_scan.py owasp.org                               # where the seconds go
```

The public sources change and fail from run to run; HackerTarget's quota is per address and per day.
