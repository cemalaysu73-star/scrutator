# Round R6: speed, recall and the report — measurements

Made on 2026-10-21 from one machine and network (Windows, the Netherlands). The four frozen targets and the criterion
of the frozen criterion (docs/benchmarks.md) were not touched. Competitors are the PyPI tools of every earlier round (sublist3r 1.0, dnsrecon
0.10.1, knockpy 9.0.0); their results are those of run a (`bench/results/2026-10-20-r4-a`), re-scored against this
run's pseudo-truth; only Scrutator was run again. subfinder, Amass, SpiderFoot and theHarvester were **not run**
(they need an executable or a repository download). Anything that did not run is marked so, never guessed.

## Speed (task 1)

Measured with `bench/ttfn.py`: three rounds, the two versions taking turns 90 s apart, each run the benchmark's own
command (`scan <target> --format json --ai off --no-summary --bundle`) in a fresh child process, so every number
includes Python start-up (about 2.5 s on this Windows machine) and the signed bundle. "Before" is the source of
`5fc8a21` (1.0.0rc1); "after" is `d37121a` (task 1 only). The before version prints no names while it runs, so the
first name a user can see is in the report written at the end. Raw: `bench/results/2026-10-21-r6/ttfn-*.json`.

| Target | Measure | Before (3 runs) | median | After (3 runs) | median |
|---|---|---|---:|---|---:|
| owasp.org | first verified name visible | 35.97, 29.24, 28.95 (end of scan) | **29.2 s** | 8.64, 4.11, 7.04 | **7.0 s** |
| owasp.org | full scan | 35.97, 29.24, 28.95 | 29.2 s | 30.34, 25.54, 16.70 | 25.5 s |
| owasp.org | `quick` (whole command) | — | — | 8.51, 6.41, 6.97 | **7.0 s** |
| owasp.org | `quick`, first name | — | — | 3.89, 3.84, 4.09 | 3.9 s |
| nmap.org | first verified name visible | 11.59, 12.78, 11.56 (end of scan) | **11.6 s** | 4.67, 10.49, 4.54 | **4.7 s** |
| nmap.org | full scan | 11.59, 12.78, 11.56 | 11.6 s | 17.97, 19.22, 12.18 | **18.0 s (slower)** |
| nmap.org | `quick` (whole command) | — | — | 13.59, 12.72, 10.74 | **12.7 s (target 10 s missed)** |

The live names found were the same in every pair (owasp.org 54/48/48, nmap.org 5), and every name the live list
printed was `verified` in that run's report (also a threshold of `scrutator bench`, section `recall_speed`).

Reading:

- **The felt speed is the win.** A user sees verified names after 4-7 s instead of only at the end. `quick` meets the
  10 s target on owasp.org and misses it on nmap.org, where 340 names resolve only to the zone's wildcard.
- **The full scan is not reliably faster.** owasp.org's median fell 13% (29.2 to 25.5 s); nmap.org's rose from 11.6 to
  18.0 s, two of three runs slow, cause not pinned down. A single in-process profile (`bench/profile_scan.py`,
  owasp.org 30.0 to 18.3 s, `bench/results/2026-10-21-r6/profile-before-owasp.json` for the before side) had suggested
  more; the interleaved runs are the measurement. What the profile does show: RDAP left the critical path (finished by
  6.7 s instead of 29.5 s; public addresses now go straight to their registry), and RIPEstat dropped from 144 to 87
  requests (asked once per network).
- **Task 2 costs time.** The crt.sh database fallback (below) waits 20-30 s when crt.sh's web search is down, which it
  was all day; it is not in the table above but it is in the benchmark below (owasp.org 47 s).

## Recall (task 2): the competitor benchmark

`python bench/run_bench.py --date 2026-10-21-r6-final --reuse-from bench/results/2026-10-20-r4-a --rerun scrutator`,
Scrutator 1.0.0rc2 at `4c1e2e3` plus the IP.THC.ORG cap below. Raw: `bench/results/2026-10-21-r6-final/`.

| Target | Truth | Scrutator R5 (`2026-10-21-r5`) | Scrutator R6 | Best competitor | Evidence-backed | Bundle verifies (pinned) | Tamper detected | Met |
|---|---|---|---|---|---|---|---|---|
| zonetransfer.me | 31 zone names | 13% (4 live), 13.8 s | 13% (4 live), 23.3 s | knockpy 6% | 100% (6) | PASS | yes | **yes** |
| example.com | 1 live name | 100%, 12.5 s | 100%, 21.8 s | sublist3r, knockpy 100% | 100% (998) | PASS | yes | yes (tie) |
| nmap.org | 4 live names | 100%, 10.9 s | 100%, 20.1 s | knockpy 100% | 100% (349) | PASS | yes | yes (tie) |
| owasp.org | 61 live names (union) | 89% (47 live), 30.0 s | **97% (59 live)**, 47.1 s | knockpy 72% (44) | 100% (138) | PASS | yes | **yes** |

**The frozen criterion is met on all four targets.** crt.sh's web search failed on every target again; its database
answered on every one (each report holds a `PGSQL crt.sh:5432/certwatch identities <target>` record), so for the first
time since R4 Scrutator had crt.sh's data in a benchmark run. Sources that failed this run: CertSpotter and Common
Crawl on every target.

Where owasp.org's twelve new live names came from (sources naming each, from the report): 12 of the 13 new names are
named by IP.THC.ORG and/or the crt.sh database, the two sources added this round that do not depend on HackerTarget's
50-a-day quota; HackerTarget answered in this run (it did not in R5), and one new name (`aivss`) is named by it alone.
So part of the gain is a quota day, and most of it is not.

What did **not** add anything on these targets:

- **Mined mentions** (in-scope names written inside evidence already held): 0 new names on all four targets. The
  existing modules already extract every name those payloads carry; the mechanism is tested and on, and measured to
  add nothing here.
- **`--axfr --active` on zonetransfer.me**: from this network both name servers time out on TCP 53 for a transfer
  (SOA over TCP answers in 0.06 s; the AXFR gets no byte in 15 s, raw socket and dnspython alike), as in R4 and R5.
  The scan records both as evidence (`TIMEOUT: no transfer within 10 s`) and the recall stays 4 of 31.
  `bench/results/2026-10-21-r6/axfr-zonetransfer.txt`. The code is proven against a local AXFR responder
  (`tests/test_r6_recall.py`, `scrutator bench` section `recall_speed`: 5 of 5 planted names), not against the real
  zone. **The one real truth set is still at 13%.**
- **NSEC walking**: not built. zonetransfer.me, nmap.org and owasp.org are unsigned and example.com uses compact
  denial, so it could not add a name on any frozen target.

### A regression caught on the way

The first run after task 2 (`bench/results/2026-10-21-r6-bench`) failed the criterion on example.com: **0% recall**.
IP.THC.ORG returned about 5,000 names for example.com (almost all junk), the scan reached its 5,000-entity cap, and at
the cap no new lookup starts, so not even `www.example.com` was resolved. IP.THC.ORG is now capped at 500 names per
answer, like the other free aggregators; the run above is after that fix. The underlying behaviour (a noisy source can
fill the cap before DNS runs) is still there and is listed below.

## What is still weak

1. **The real truth set is at 13%.** The zone transfer that would reach the other 27 names is blocked from this
   network; nothing passive reaches them.
2. **The full scan got slower on nmap.org and is slower again with the crt.sh database** (20-30 s when the web search
   is down). The felt speed improved; the end-to-end time did not, reliably.
3. **`quick` misses 10 s on a wildcard zone** (nmap.org 12.7 s).
4. **A noisy source can still fill the entity cap before DNS runs** (the IP.THC.ORG regression; capped, not cured).
5. **Pseudo-truth is circular** for three of four targets, and the strongest passive tools were not run.
